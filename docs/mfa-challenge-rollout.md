# MFAチャレンジの導入とローカル検証

## 認証APIの仕様

`POST /internal/authentication` に `type: "password"` を指定すると、パスワードを検証します。
有効なアカウントでTOTPが有効になっている場合、セッションを作成せず、
`require_mfa: true`、`mfa_type`、`mfa_challenge` を返します。
チャレンジは暗号学的に安全な256ビットの乱数を、43文字のbase64url形式で表した
opaqueなBearerトークンです。MySQLにはトークンのSHA-256ハッシュのみを保存し、
ユーザーID、remember設定、作成日時、有効期限、試行回数、消費日時を紐づけます。

`type: "totp"` では `mfa_challenge` と `code` が必要です。
認証対象のユーザーはチャレンジから特定します。任意項目のユーザー名が指定された場合は、
そのユーザーと一致する必要があります。Authは有効期限（5分）、試行回数（最大5回）、
消費状態、現在のアカウント状態、TOTP設定を検証します。
MySQL/InnoDBの `SELECT ... FOR UPDATE` により、複数のAuthプロセスからの試行も直列化します。
認証失敗時は、増加させた試行回数をコミットします。認証成功時は、同じトランザクション内で
チャレンジを消費し、セッションを作成してJWTに署名します。
DB処理や署名のエラーが発生した場合は、トランザクションをロールバックします。
チャレンジなしで認証できる旧経路は、互換性のためにも残しません。

Frontではパスワード用とMFA用のServer Actionを分離しています。
MFA用Actionは、フォームから送信されたユーザー名やチャレンジではなく、
HttpOnly Cookieからチャレンジとユーザー名を取得します。
CookieにはSameSite=Lax、Path=/、有効期間5分を設定し、本番環境ではSecureも設定します。
ログイン成功時にはMFA待機用Cookieを削除します。
remember設定を含め、認証判断の根拠となるのはAuthのDBに保存された情報です。
TOTP無効ユーザーのパスワードのみでのログインは引き続き利用できます。
セッションの有効期間は7日／30日（remember有効時）のままで、既存のセッションCookieの
有効期間も変更していません。

## 導入手順

1. 新しいAuthを起動する前に、既存のマイグレーション手順で
   `UniQUE-DB/migrations/22_mfa_challenges.up.sql` を適用します。
   テーブルのストレージエンジンにはInnoDBを使用する必要があります。
2. AuthとFrontの更新を協調して実施します。ログインの受付を再開する前に、
   旧Authインスタンスへの認証リクエストの振り分けを停止します。
   旧AuthはチャレンジなしのTOTPリクエストを受け付けるため、新旧Authの混在は安全ではありません。
3. 新しいFrontを導入します。新Authと旧Frontの組み合わせでは、安全側に倒してMFAログインが
   失敗します。旧形式のMFA待機用Cookieが残っているユーザーは、パスワード認証からやり直す必要があります。
4. 通常のトラフィックを戻す前に、ステージング環境でパスワードのみのログイン、MFAログイン、
   セッション検証、OIDCクライアントのフローを確認します。

旧Authへのロールバックは脆弱性を再導入します。ロールバックが必要な場合は、
旧TOTP認証経路を復活させるのではなく、認証境界でMFAログインを無効化してください。
新Authの稼働中にチャレンジテーブルを削除しないでください。
downマイグレーションは待機中のチャレンジをすべて削除しますが、セッションは削除しません。

期限切れの行は、DBから削除されていなくても認証に使用できません。
保守ジョブで以下のSQLを繰り返し実行するなど、一度に処理する件数を制限して定期削除してください。

```sql
DELETE FROM mfa_challenges WHERE expires_at < UTC_TIMESTAMP() LIMIT 1000;
```

DBとアプリケーションの時刻を同期してください。
マイグレーション適用後に `make auth-gen` と `make api-gen` を実行して、
`mfa_challenges` のGORMモデルと型安全なクエリを再生成してください。
生成物は手編集せず、スキーマ変更時には同じ手順で更新します。

## 自動テスト

使い捨てのMySQLデータベースのみを使用してください。
`MFA_TEST_DSN` を指定すると、Goの統合テストがテスト用のテーブル・ユーザー・セッションを作成します。
これには、実際のマイグレーション22で作成するテーブルも含まれます。
共有の開発用DBや本番DBを指定しないでください。
この環境変数がない場合、DB統合テストは明示的にスキップされます。

`UniQUE-Auth/src` で実行します。

```sh
MFA_TEST_DSN='<parseTime=trueを含む使い捨てMySQLのDSN>' go test ./...
```

テストはT01～T12およびT16を対象としています。パスワード・TOTP認証の成功、
チャレンジの欠落・偽造、誤ったパスワード・コード、ユーザー不一致、期限切れ、再利用、
8件の並行リクエスト（作成されるセッションは1件のみ）、5回の試行上限、remember設定の紐づけ、
パスワードのみのログイン、存在しないユーザーを検証します。
さらに、無効化・削除されたアカウント、TOTPシークレットの削除、JWT署名失敗時のロールバックも確認します。
認証拒否時には、HTTP 401、JWT・チャレンジが返らないこと、セッション行が増えないことを検証します。

`UniQUE-Front` で実行します。

```sh
bun test ./src/components/Pages/Authentication/components/actions/signIn.test.ts
bunx tsc --noEmit
bun run build
```

プロセスをまたぐ結合テストでは、`MFA_TEST_DSN` に加えて `MFA_TEST_HTTP=1` を指定して
Goのテストを起動します。テストに成功すると、実際のAuthハンドラーとテストデータ取得用の
専用エンドポイントが、ポート8080で3分間起動します。
このポートは隔離されたローカルのコンテナネットワーク内でのみ使用し、外部に公開しないでください。
テスト用パスワード、TOTPコード、生成された鍵をログに出力しないでください。
起動後、以下を実行します。

```sh
MFA_TEST_AUTH_URL=http://<test-auth>:8080 bun test ./src/components/Pages/Authentication/components/actions/signIn.test.ts
```

実HTTP経由のServer Action回帰テストでは、ビルド済みのNext.jsサーバーを
`AUTH_API_URL=http://<test-auth>:8080` を指定して起動します。
その後、同じFrontのチェックアウトで以下を実行します。

```sh
MFA_TEST_AUTH_URL=http://<test-auth>:8080 MFA_TEST_FRONT_URL=http://<test-front>:3000 bun test ./tests/mfa-http.test.ts
```

HTTPテストは、ローカルのビルドマニフェストからAction IDを取得します。
マニフェスト自体はログに出力しません。
Cookie・パスワードなしで有効なTOTPのみを送るリクエスト、実際の `Set-Cookie`、
DBのセッション件数、パスワード→チャレンジ→TOTPの正常系、再利用の拒否、
Frontの実際のJWT署名検証・セッション検証を経た `/device/consented` へのアクセスを確認します。
Actionテストでは、OIDCの戻り先URLが維持されることも確認します。
Actionテストは `next/headers` をモックするため、Frontの2つのテストスイートは別プロセスで実行してください。

## 検証記録と未検証範囲・残課題

2026-10-20のローカル検証では、Go 1.26およびMySQL 26.7のコンテナと、
Bun 1.4.3／Next.js 16.2.7を使用しました。
起動済みの開発スタックは別のチェックアウトを参照していたため、今回の変更には専用のテストコンテナを使用しました。

- Auth `go test ./...`：使い捨てMySQLに対して成功。
- Auth `CGO_ENABLED=1 go test -race ./...`：並行実行と署名失敗時のロールバックの確認を含めて成功。
- FrontのActionテスト：実Authとの結合を含む6件が成功。
- ビルド済みNext.jsのHTTPテスト：実際のSet-Cookieと保護ページへのアクセスを含む1件が成功。
- TypeScriptのno-emit型検査と本番ビルド：成功。
- 変更したFrontファイル：Biomeによる整形・lintを適用して確認済み。
- dashboard全体の描画と、外部OIDCクライアントでの認可コード・トークン交換：
  これらのテストでは未実施。通常のdashboardへの戻り先とOIDCの戻り先URLはActionレベルで確認済み。
  ブラウザ操作によるUIテストは未実施。

調査したローカルソースの旧TOTP認証経路は、提示された引継書の内容と一致していました。
パスワード認証では、存在しないユーザーを既に401として扱っていました。
チャレンジ方式のTOTP認証では、送信された任意のユーザー名を使って認証対象を検索しなくなりました。
引継書のMarkdownファイルはこのチェックアウト内に存在しなかったため、提示された本文を使用しました。
調査した認証フローには、既存のRedis・チャレンジストアやログインのレート制限は見つかりませんでした。
今回、Authでチャレンジ単位の試行回数を制限しましたが、アカウント・IP単位での
パスワード認証やチャレンジ発行の制限は、追加の強化策として残っています。
パスワード認証済みの複数のチャレンジは同時に存在でき、同じ時間ステップのTOTPコードを
異なるチャレンジ間で一度しか使えないようにする制限はありません。
チャレンジは引き続きBearer認証情報であるため、内部通信を保護し、リクエスト・レスポンス本文、
Cookie／Set-Cookie、認証ヘッダーを診断ログの出力対象から除外してください。
今回の変更でトークン・コード・シークレットのログ出力は追加していません。

## 非公開Security Advisoryへの反映事項

この問題は「有効なTOTPを利用できる場合に、TOTP有効ユーザーのパスワード要素を迂回できる」と記載し、
「未認証で任意のアカウントにアクセスできる」とは表現しないでください。
Authが強制する短寿命のパスワード認証済みチャレンジ、原子的な一度限りの消費、
試行回数の上限、Frontの変更内容を記録してください。
ローカル検証では、有効なTOTPのみを送信してもセッションCookie・セッションレコードが作成されず、
正常なMFAでは検証可能なセッションが作成され、保護ページにアクセスできたことを記録してください。
未検証のdashboard全体・OIDCフルフローや本番での到達性と、これらのローカル結果を区別してください。
CWE-287は引き続き適切な分類候補ですが、今回のテストで本番のCVSSベクトルを確定したり、
修正前に発行されたJWTで保護ページへアクセスできたことを遡って証明したりすることはできません。
詳細は非公開Advisoryのレビュー手順で共有してください。
